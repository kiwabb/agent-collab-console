# 结构化原型生成与编辑最终目标

## 最终结果

交付一个领域无关、产品经理可实际使用的端到端结构化原型系统：

1. 任意已接入且源码可读的项目，都能由项目绑定的 Claude Code `prototype_ui_engineer` 基于仓库证据和用户意图生成原型蓝图。
2. 页面、路由、导航、业务对象、角色、表单和流程均来自项目证据与已确认蓝图，不在生产代码中预设采购、审批或任何其他业务领域。
3. 生成结果是统一版本的结构化文档，不是互不关联的 HTML；页面共享导航和设计令牌，可在 Studio 中继续编辑。
4. 产品经理可以拖拽和编辑语义组件，也可以通过 AI 对话提出修改，预览后 Apply 或 Reject。
5. 只有项目确实存在业务交互时才生成对应的实体、表单、角色、规则和可重放场景；静态或只读项目不得被迫编造业务流程。
6. 结构化文档、领域命令、checkpoint、runtime event、AI task/submission、render 和 publish 每一步都可观测、可恢复、可重放。
7. 发布一个可运行、可分享、由固定 renderer/runtime 版本生成的预览产物。

## 通用边界

```text
项目数量：不设业务领域限制
页面数量：由蓝图决定，受结构化契约上限约束
角色 / 实体 / 表单 / 流程：按项目证据可选
语义组件：使用结构化组件契约支持的类型
业务内容：生产代码中零领域硬编码
```

首版不包含真实 API/数据库接入、真实认证授权、生产数据、任意脚本/表达式、完整 BPMN、多人协作、Figma/Penpot 格式兼容或生产代码导出。

## `admin-demo` 验收对象

`examples/admin-demo` 只用于验证通用链路，不是默认模板，也不是生成器的业务来源。验收时系统应从项目源码识别并生成：

1. 仪表盘 `/dashboard`
2. 用户管理 `/users`
3. 订单管理 `/orders`
4. 与项目现有信息架构一致的共享导航、页面内容和可编辑语义节点

任何生成产物中出现采购申请、采购审批、申请人或主管角色，都应视为生产硬编码仍未清除。

## 验收闭环

产品经理必须能够在不查看源码的情况下：

1. 打开任意项目的原型设计入口，不填写固定业务模板需求也能启动项目分析。
2. 查看并确认由项目证据产生的动态多页面蓝图。
3. 生成完整结构化原型并进入 Studio。
4. 拖动组件、编辑属性并保存。
5. 要求 AI 修改文案、布局或项目已有的简单业务规则，并预览/应用。
6. 刷新后恢复设计状态；存在 runtime 场景时，重放得到相同 final state/view-model hashes。
7. 发布并打开可运行预览。

## 实施顺序

1. 清除生成提示词、装配器、持久化约束和 UI 文案中的采购业务耦合。
2. 将蓝图定义为页面与可选业务意图的唯一生成范围，所有后续任务只消费确认后的蓝图。
3. 实现领域无关的确定性文档装配与结构校验，并对可选 runtime 场景做相应验证。
4. 使用 `admin-demo` 完成项目分析、蓝图确认、生成、编辑、恢复和发布的端到端验收。
5. 增加第二个最小非后台管理 fixture，证明通用性不是对 `admin-demo` 的另一种硬编码。

任何阶段都不能用新的固定模板代替项目驱动生成。
