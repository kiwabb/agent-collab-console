### 发现 A（小｜状态徽章不同步）：自主编排时 issue 一直显示"排队中"

详情页左上角状态徽章在 Conductor 全程运行期间仍显示 **「排队中」**（`issue.status="open"`），只有 CONDUCTOR 阶段那块（`awaiting_subagent` 等）正确反映在跑。

**根因**：auto-start 自主编排路径下，Conductor 开始 dispatch 后**从不把 `issue.status` 翻成 `in_progress`**——`conductor_main_loop.py` 只在收尾 `_seal_graph_and_issue_status`（:767-779）一次性把 open→completed/failed。`in_progress` 仅在 plan-approval 等端点（`api.py:2684 / :2755`）设置，自主编排不经过那里。所以 issue 级状态从 open 直接跳到 completed/failed，中间的"运行中"被跳过。

**影响**：纯展示层不一致，不影响编排逻辑。建议修复：Conductor 第一次 dispatch（或 loop 启动）时把 issue 置 `in_progress` 并发 `issue_updated`。

### 发现 D（真实｜小显示 bug，复现上轮所述）：cmux hook JSON 泄进 dispatch 摘要

时间线第 1 个事件标题渲染成：
`08:43 ARCHITECT DONE 4m11s 已分发 architect {"type":"system","subtype":"hook_started","hook_name":"SessionStart:resume",...}`

后半段那串原始 JSON 是 **cmux 包裹的 claude CLI 第一行流式输出**（`SessionStart:resume` hook 的系统事件），被 subagent 结果摘要提取逻辑当成了正文。第 2、3 个 engineer 事件没这串（它们第一行不是 hook）。这是确定的小 bug：dispatch 行摘要应过滤掉 CLI 的 hook/system 行。**建议修复**：摘要提取处跳过 `type==system` / `hook_*` 的行。

### 根因复盘（与上轮一致｜executor 质量）：minimax 卡死 + 空结果

engineer#1 的 task_messages 里出现：

## 🔴 走查暴露的真正根因（高价值发现）：执行器选择**完全没生效**

「换 Codex 跑通收尾」失败，根因不是 Codex 不行，而是**根本没用 Codex**：

- 数据实测：issue `d99d5863` 我明确选了 **Codex / gpt-5.5**，但所有 6 个 subagent（PM/architect/engineer×N）的 `model` 全是 **MiniMax-M2.7**。
- 原因链：
  1. `codex_issues` 表**没有 executor/provider/model 列** —— 新建弹窗收集的执行器/模型选择**根本没存到 issue 上**。
  2. `task_dispatcher.py:89-91` dispatch subagent 时，executor/model 取自 **agent 目录的 default**（`agent.default_executor/model`），与 issue 无关。
  3. 所以新建弹窗的「执行器」下拉对 Conductor 流程是**装饰性的**——subagent 永远跑 agent 默认（minimax）。
- 后果：subagent 实为 minimax（经 `claude -p --model MiniMax-M2.7` 跑，所以既是 minimax 模型又带 cmux hook）→ 停滞被 watchdog 催 → engineer 被催后还**输出了 architect schema 的 JSON**（不含 changed_files）→ `refresh_task_result` 解析失败 → 判 failed → Conductor 反复重派 → 不收尾。

**结论**：要真正「用 Codex 跑通收尾」，必须先修执行器传递——把 issue 级 executor/model 持久化并贯穿 `run_issue_conductor_loop → dispatch_subagent → dispatch_role`，覆盖 agent 默认。这是个需要 schema + 多层串联的正式改动，需先和用户对齐设计。

## 第四阶段：修 Codex 收敛（gpt-5.5 跑不通的真因）

走查发现 gpt-5.5 这轮也不收尾：每个 engineer 精确卡满 **900s**（`dispatch_subagent` registry 超时，conductor_tools.py:88），tool_result 是 `{"error":"subagent timed out after 900s"}`。逐层定位：

**真因：codex app-server 的 model 在 `__init__` 时一次性写死，忽略 task 的 model。**
- `codex_app_server_runtime.py:48` `_build_app_server_cmd` 用 `os.getenv("CODEX_APP_SERVER_MODEL","gpt-5.4-mini")` 把 `-c model=gpt-5.4-mini` 烤进 cmd（构造时一次）。
- launch 时（:277）只把 task model 设成**环境变量** `CODEX_APP_SERVER_MODEL`，但 codex CLI 认的是 `-c model=` 命令行参数，**不认环境变量** → 不管选什么模型，app-server 永远跑 `gpt-5.4-mini`。
- 日志实证：选 gpt-5.5，spawn 行却是 `-c model=gpt-5.4-mini`。

**修复**：新增 `_with_model_override(cmd, model)`，launch 时按 task 的已解析 model **重写 cmd 里的 `-c model=` 参数**（无则追加）。3 例单测通过。
- 验证：新建 codex/gpt-5.5 issue 后，日志 spawn 行变成 `-c model=gpt-5.5` ✅（修复前是 gpt-5.4-mini）。

> 注：日志还显示 codex app-server 反复 `Handshaking...` + 收到 chat-mode override —— 若 gpt-5.4-mini 本身不可用导致握手/turn 起不来，换成有效的 gpt-5.5 后应能握手并完成 turn；正在监控这轮 gpt-5.5 是否真正完成（不再 900s 超时）。codex CLI 版本 0.132.0。

### 🎯 真正的根因（Codex 完全不可用的元凶）：app-server 启动参数非法即崩溃

进一步排查 gpt-5.5 仍 900s 超时：engineer 日志只有一行 `Handshaking...` 后**零 stdout**，且后端日志刷屏 `[AsyncJSON-RPC] Failed to send: Connection lost` —— 说明 **codex app-server 进程一启动就死了**。

直接复现（codex CLI 0.132.0）：
```
$ codex app-server -c model=gpt-5.5 --permission-mode=bypassPermissions --permission-prompt-tool=stdio
error: unexpected argument '--permission-mode' found       # exit code 2
$ codex app-server -c model=gpt-5.5                         # 不带这俩 flag → 存活，且 initialize 正常响应
```

**根因**：`codex_app_server_runtime.py:_build_app_server_cmd` 给 `codex app-server` 追加了 `--permission-mode=bypassPermissions` 和 `--permission-prompt-tool=stdio`，但 **0.132.0 的 app-server 不认这两个参数 → 立即 exit 2**。于是每次 dispatch 的 app-server 都瞬间崩溃 → 所有 send `Connection lost` → 永远收不到 turn 通知 → `dispatch_subagent` 900s 超时 → Conductor 无限重派。这就是 **Codex 完全走不通的元凶**。

**修复**：从 `_build_app_server_cmd` 删除这两个非法 flag（权限本就由 JSON-RPC 审批回调 `AppServerClient._on_server_request` 自动批准，CLI flag 既非法又多余）。修复后 `_build_app_server_cmd` 输出 `['codex','app-server','-c','model=...']`，进程存活、initialize 正常。

正在用 healthz5（codex/gpt-5.5）端到端验证：app-server 不再崩溃、turn 正常完成、流程能收尾。

### 🎯🎯 最终根因（Codex 一直起不来的真凶）：PATH 让 codex 跑在坏掉的 Homebrew node 上

修了非法 flag 后，app-server 仍立即死（`Connection lost` 刷屏、0 个 JSON-RPC 通知）。直接捕获 app-server stderr：
```
dyld: Library not loaded: /opt/homebrew/opt/llhttp/lib/libllhttp.9.3.dylib
  Referenced from: /opt/homebrew/Cellar/node/25.9.0_2/bin/node
```

**根因**：`codex` 是个 Node 脚本，靠 PATH 找 `node`。本机 `/opt/homebrew/bin/node` 是 **Homebrew node 25.9.0，缺 `libllhttp.9.3.dylib`（坏的）**；可用的是 `node@24`（v24.15.0，在 `/opt/homebrew/opt/node@24/bin`）。后端进程自身 PATH 里 node@24 在前（可用），但 `codex_app_server_runtime.py:300` 把 `/opt/homebrew/bin` 等**前插**到 PATH 最前，于是 codex 跑在坏 node 上 → dyld 崩溃 → 进程秒退 → 所有 send `Connection lost` → 0 通知 → 900s 超时 → 无限重派。这就是 Codex 从头到尾完全起不来的真凶（前面的非法 flag 是第一层，这个坏 node 是第二层）。

**修复**：把 fallback 路径从**前插改成追加**（`existing_PATH + fallback`），保留后端已有 PATH（node@24 优先）。fallback 只在 PATH 缺失时兜底，不再 shadow 可用 node。

**验证（issue dc8327ea, codex/gpt-5.5）**：修复后
- `Connection lost` 增量 = **0**（app-server 不再崩溃）✅
- JSON-RPC 通知从 0 → **590 条**（`turn/started` / `item/started` / `item/reasoning/summaryTextDelta`×325 / `thread/tokenUsage/updated`…）——turn 真正在跑并流式输出 ✅

> 注：本机的 Homebrew `node` 25.9.0 是坏的（缺 llhttp），属环境问题；本修复让 runtime 不再强行用它。建议用户也修一下那个 node（`brew reinstall llhttp node` 或卸载坏的 25.9.0），否则任何 PATH 里 `/opt/homebrew/bin/node` 在前的场景都会踩到。
